# HLTV.org — reverse-engineering notes

Everything here was established by probing the live site on **2026-11-24**, not from documentation.
HLTV publishes no API docs; these are the endpoints and markup the public pages actually use.

## 1. Method

1. Installed [`reverse-api-engineer`](https://github.com/kalil0321/reverse-api-engineer) v0.16.0
   (`uv tool install "reverse-api-engineer[manual]"`).
2. `reverse-api-engineer agent --dry-run --headless ...` passed all checks, but the real run stopped at
   the model boundary:
   `! error: Not logged in · Please run /login` (the Claude Agent SDK has no `ANTHROPIC_API_KEY` and
   cannot see a Claude Code login in its isolated session). **No client was generated by the tool.**
3. Capture was therefore done directly: a real Chromium session (the Cloudflare pass is the same one
   RAE's `chrome-mcp` / `auto` providers rely on), then in-page `fetch()` probes and `DOMParser`
   inspection of each page. Findings below are the observations, and `src/parse.ts` is the client
   that was generated from them.

## 2. Cloudflare is the first obstacle

| Client | `GET /matches` | Result |
| --- | --- | --- |
| `curl` (UA only) | 403 | Cloudflare |
| `curl` (full browser header set) | 403 | Cloudflare |
| Node `fetch` (undici, full header set) | 403 | `Just a moment...` challenge page, ~5.8 KB |
| Real headless Chrome | 403 | challenge never cleared |
| Headful Chrome, reused context | mixed | first page ok, later pages challenged |
| Headful Chrome, new context per request | 200 | 3/3 pages, ~1 s each |
| curl-impersonate `--impersonate chrome136` | 403 | TLS profile rejected |
| curl-impersonate `--impersonate chrome131` | **200** | 687 KB document, every endpoint |

Consequences for any client:

- Cloudflare challenges **document** requests; its block is TLS/JS based, so spoofing headers is not enough.
  `--impersonate chrome131` passes because it reproduces Chrome's TLS ClientHello + HTTP/2
  fingerprint; `chrome136` does not, so the profile has to be one Cloudflare still accepts.
- Headless Chrome is detected; a real window is not. Reusing one browser context gets challenged
  after the first page — a fresh context (or clearing cookies) per request fixes it.
- `/api/*` endpoints are *not* challenged (`401` arrives directly) — but they are auth-only.
- Two workable transports: drive a real browser (used here), or reuse a browser's `cf_clearance`
  cookie with a matching UA/IP (fragile; `mode: 'fetch'` supports it).
- Requests are serialized in this client to avoid hammering one session. No documented rate limit was
  observed; keep concurrency at 1 and keep the `delayMs` default.

## 3. Endpoint map

Probed with an authenticated (Cloudflare-cleared) in-page `fetch`:

| Path | Status | Content |
| --- | --- | --- |
| `/matches` | 200 | HTML, live + upcoming matches; `?event=`/`?team=` are applied by JS in the browser, the document is identical (238 cards) |
| `/results?offset=0` | 200 | HTML, finished matches; `offset` steps by 100 |
| `/results?startDate=YYYY-MM-DD&endDate=YYYY-MM-DD` | 200 | HTML, date-filtered, grouped under `Results for <date>` headings |
| `/results?event=<id>` | 200 | HTML, results of one event |
| `/events` | 200 | HTML, ongoing + upcoming events by month |
| `/events/<id>/<slug>` | 200 | HTML, event overview (dates, prize/spots, teams count, location) |
| `/event/<id>/<slug>` | 200 | Same page as `/events/...` (both resolve) |
| `/matches/<id>/<slug>` | 200 | HTML, match detail (teams, scores, per-map results) |
| `/stats/matches?startDate=&endDate=` | 200 | HTML, stats index (not wrapped by this client) |
| `/search?query=<q>` | 200 | HTML, site search |
| `/matches/archive` | 200 | HTML, archive browser |
| `/api/matches` | **401** | exists, requires HLTV session auth |
| `/api/events` | **401** | exists, requires HLTV session auth |
| `/api/teams` | **401** | exists, requires HLTV session auth |
| `/api/streams` | **401** | exists, requires HLTV session auth |
| `/api/v1/matches`, `/api/v1/events` | 404 | no versioned API |
| `/api/players`, `/api/event`, `/api/ranking`, `/api/stats`, `/api/news`, `/api/user`, `/api/search` | 404 | not routed |
| `/matches/load-more/<n>` | 400 | exists but rejects this shape (needs the site's own params) |
| `/api/ads/rendered/[...]` | 200 | ad slot rendering, irrelevant |

`<slug>` is cosmetic — `/matches/2400564/x` and `/events/9303/x` resolve to the same document.

## 4. Live scores: scorebot

- `<body data-livescore-server-url="https://scorebot-lb.hltv.org">` is the live-score server.
- Every live card carries `data-livescore-match="<matchId>"`, and `.match-fixtures-placeholder[data-match-id]`
  is where the JS injects the score.
- `scorebot-lb.hltv.org/socket.io/?EIO=4&transport=polling` handshake answered `403` to plain HTTP
  (same Cloudflare wall), so it must be reached from a browser context.
- Therefore the HTML gives you *which* match is live, not the running score.

## 5. Selectors the parsers rely on

### `/matches` — `MatchCard[]`

```
.match                                   ← outermost card (live cards nest a second .match)
  a[href^="/matches/"]                   → id + slug
  .match-event[data-event-id][data-event-headline]  → event id/name, img.match-event-logo
  .match-stage                           → stage label ("match-pre-playoff" shows as text)
  .match-rating i.fa-star:not(.faded)    → 0-5 stars
  .match-meta                            → "Live", "bo1", "bo3"
  .match-time[data-unix]                 → start time in ms (absent on live cards)
  .match-team .match-teamname + img      → team1, team2 (logos: skip .night-only duplicates)
```

### `/results` — `MatchResult[]`

```
.results-sublist > .result-con
  data-zonedgrouping-entry-unix          → per-row timestamp in ms
  a[href^="/matches/"]                   → id + slug
  td.team-cell .line-align.team1/.team2  → .team (class contains team-won), img[alt] logo
  td.result-score .score-won/.score-lost → series score
  td.event .event-name                   → event (no id: the cell is not a link)
  td.star-cell .map-text                 → map abbreviation ("mrg", "inf", "d2")
  td.star-cell .stars i.fa-star          → starred/featured
```

The flat `/results` list has **no day headings**; `Results for <date>` headings only appear in the
date-filtered view (`?startDate=…&endDate=…`).

The page contains two holders and only the second is the real list:

| Holder | Rows | Timestamps |
| --- | --- | --- |
| `.results-holder.results-all` ("Featured results") | 16 | none |
| `.results-holder.allres` | 100 per page | `data-zonedgrouping-entry-unix` on each `.result-con` |

### `/events` — `EventSummary[]`

```
.ongoing-event                            → a[href^="/events/"], .event-name-small .text-ellipsis,
                                           .lan-marker (strip: it is concatenated), .top-team-logos img[title]
.events-month (inside .events-holder)
  .standard-headline                      → month label
  .big-event                              → a.standard-box.big-event: .big-event-name,
                                           .big-event-location, img.flag[title],
                                           .additional-info .col-date [data-unix] x2,
                                           .col-value[title="$80,000"], teams count cell
  a[href^="/events/"]:not(.big-event)     → ordinary event cards
```

The page ships desktop + mobile copies of ongoing cards, so duplicates must be dropped by id.

### `/matches/<id>/<slug>` — `MatchDetail`

```
.team1-gradient / .team2-gradient         → .teamName, .won/.lost score, img logo
a[href^="/team/"]                         → team ids in appearance order
.mapholder
  .mapname                                → map name
  .results-left/.results-right            → .won/.lost marker + .results-team-score
  .results-center-stats a[href*="/stats/matches/mapstatsid/"]  → per-map stats id
.date[data-unix]                          → start time
a[href^="/events/<id>/"]                  → event link (prefer the one with a title attribute:
                                            .dropdown-link only holds the shortened name)
```

The series format (`bo1`/`bo3`) does **not** appear anywhere in the match document text — it exists
only on the match card, hence no `format` in `MatchDetail`.

### `/events/<id>/<slug>` — `EventDetail`

```
.event-header-component table.info
  thead th.eventdate / th.prizepool / th.teamsNumber / th.location
  td.eventdate [data-unix] x2             → startsAt, endsAt
  td.prizepool[title]                     → "$1,250,000" or "Spots in Stage 2"
  td.teamsNumber                          → 16
  td.location .text-ellipsis + img.flag   → "Singapore"
img[src*="eventlogo" | "eventbanner"]     → event artwork (teamlogo URLs are team crests)
```

## 6. Not implemented

- `scorebot-lb.hltv.org` websocket/polling feed (live round-by-round scores).
- `/api/*` authenticated endpoints (no token source that is legal to automate).
- `/stats/*` aggregates, news, forum, players, rankings, team pages.
- Any claim of a documented rate limit: none was found; be conservative.
